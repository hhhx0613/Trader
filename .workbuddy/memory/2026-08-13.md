## 排查 LLM 缓存命中问题

用户问题：第一次跑完整回测（不含 PPO）LLM response 都写进 SQLite 缓存，第二次跑时"有些"没命中，怀疑是 L1 记忆导致。

结论：
- 缓存 key = `(symbol, date, model)`，定义在 `agents/llm_analyst.py` 的 `_compute_cache_key`，**完全忽略 prompt 内容**（system_prompt / user_message 传入但未使用）。
- L1 记忆只注入 `_build_user_message` 的 prompt，不进 key，因此**不是 miss 的原因**；反而会带来一个反向正确性 bug（prompt 变了但 key 不变 → 二次运行错误命中旧结果）。
- ~~真正原因是 model 字段变了~~（此结论错误，已修正）。glm-4.5-air 是更早一次实验（created_at 07:04~08:22）的残留，与本次问题无关。
- **真正原因（用 created_at 把两次 deepseek 运行分开后确认）**：两次 dp 运行的缓存 key 里 `symbol`/`date` 对不上：
  1. 第一次 dp 跑（created_at 09:06~09:25）：候选池 9 只、**无 WMT**（`run_backtest_no_ppo.py`/`stage5` 默认 `DEFAULT_CANDIDATE_POOL[:9]` 恰好排除 WMT），每调仓日最多 9 条。
  2. 第二次 dp 跑（created_at 15:09~15:33）：候选池 10 只（含 WMT）→ WMT 从 08-25 到 11-24 逐日补写；且调仓日漂移出新的 08-06(6条)、08-20(10条)。
  3. V@08-11 是第一次无新闻短路未写、第二次有新闻后补写（新闻数据变化）。
- 调仓日漂移机制：`REBALANCE_WEEKLY=True` 下，调仓日 = 每个 ISO 周首个交易日，来自所有候选股日期并集 `all_dates`；候选池/`--start/--end` 一变，某周"首个交易日"就会从周一漂到别的天。

## 08-20 非周一调仓日的精确根因（已用 output 证据坐实）

- `output/stage5/llm_equity_20260812_173213.csv` 首行 = `2025-08-11` → stage5 那次 `--start=2025-08-11`（周一）。
- `output/backtest_no_ppo/llm_equity_20260812_233814.csv` 首行 = `2025-08-20` → no_ppo 那次 `--start=2025-08-20`（周三）。
- 回测引擎 `multi_stock_engine.py` 中 `prev_week_key=None`，第一天 `week_key != None` 恒真 → **回测第一天必是调仓日，不管星期几**。
- 所以 08-20（周三）就是 no_ppo 那次回测的「首周调仓日」，08-21 执行（trades 首条 = 08-21）。与候选池无关，纯粹是 `--start` 落在周三。
- 两个"非周一调仓日"来源：① 首周例外（--start 当天必调仓）；② 休市顺延（如 09-01 劳动节周一休市 → 该周首个交易日漂到 09-02 周二，执行日 09-03）。
- 从 W35（08-25 周一）起，各运行调仓日重新对齐，故后续都命中缓存。这与 `tests/test_grid_rebalance_ppo.py::test_rebalance_weekly_alignment` 的"除首周外后续对齐"完全一致。
